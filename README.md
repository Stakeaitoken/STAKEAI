# STAKEAI prototype

This repository contains the STAKEAI site and account API, a fixed-supply ERC-20/BEP-20 token, and a BNB Smart Chain testnet staking contract and wallet flow.

The landing page includes three STAKEAI assistants for coding help, general conversation, and crypto education. Their FAQ and verified STAKEAI project context are maintained in `data/assistant-knowledge.json`; the project facts are included in generative model prompts so responses can distinguish simulations from real blockchain activity. With `ASSISTANT_PROVIDER=library` (or `ASSISTANT_TEST_MODE=true`), replies come from the local FAQ and are not generated by AI or sent to an external provider. The FAQ matching follows the knowledge-base pattern demonstrated by [Rasa's open-source knowledgebasebot example](https://github.com/RasaHQ/rasa/tree/main/examples/knowledgebasebot), licensed under [Apache 2.0](https://github.com/RasaHQ/rasa/blob/main/LICENSE.txt); this project uses its architecture as a reference and contains original STAKEAI answers rather than copied example data. For local generative replies, install [Ollama](https://ollama.com/download), download [Qwen3-1.7B](https://huggingface.co/Qwen/Qwen3-1.7B), then set `ASSISTANT_PROVIDER=ollama` and `OLLAMA_MODEL=qwen3:1.7b` (or another installed model). Known FAQ answers are returned immediately; other requests are generated locally. Requests go only to the loopback Ollama service on the user's computer and do not use OpenAI API credits. With `ASSISTANT_PROVIDER=openai` (or `auto` and a configured key), chat messages are sent to OpenAI to generate replies and may be processed under its API data policies. Chat history is not saved by STAKEAI and users should not include passwords, wallet keys, or other sensitive information. Assistants are branded as STAKEAI and should not claim a particular model provider unless the configured provider is disclosed. The crypto guide offers general education, not financial advice or trade execution.

## Run locally

Requirements: Node.js 22.13 or later.

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env` and set a random `SESSION_SECRET` of at least 32 characters. For local generative replies, install Ollama, run `ollama pull qwen3:1.7b`, and set `ASSISTANT_PROVIDER=ollama` and `OLLAMA_MODEL=qwen3:1.7b`. To use OpenAI instead, set `ASSISTANT_PROVIDER=openai` and configure `OPENAI_API_KEY`; API usage is billed separately. `ASSISTANT_PROVIDER=library` uses the local FAQ without an AI model. `ASSISTANT_TEST_MODE=true` forces FAQ mode regardless of provider settings. Keep provider keys server-side and do not commit `.env`.
3. Configure SMTP (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`) and set `PUBLIC_ORIGIN` to the exact origin used in the browser, such as `http://localhost:3000`.
4. Set `ADMIN_EMAILS` to a comma-separated list of administrator email addresses. In production, create those accounts through normal registration and verify their email. For local development with a single admin address and no matching account, use the loopback-only bootstrap described below. Admin access is derived from this server-side allowlist.
5. Start the site and API with `npm start`, then open `http://localhost:3000`.
6. Register an account, follow the emailed verification link, and log in. Email verification is required; registration remains unavailable until SMTP is configured.

## Railway deployment

Railway uses `railway.json` to start the app and check `/health`; the health endpoint verifies that the SQLite database is accessible. Connect the repository's `main` branch to a Railway service and set `NODE_ENV=production`, `PUBLIC_ORIGIN` to the service's HTTPS origin, a unique `SESSION_SECRET` of at least 32 characters, `ADMIN_EMAILS`, and `SMTP_FROM`. Configure either `BREVO_API_KEY` or SMTP credentials (`SMTP_HOST`, `SMTP_USER`, and `SMTP_PASSWORD`) so email verification works. Keep all secrets in Railway variables, not in this repository.

Attach a Railway Volume to the service at `/data` and set `DATABASE_PATH=/data/stakeai.sqlite` before serving users; the default SQLite file is not persistent across Railway deploys. Back up the volume regularly. Configure token/staking contract addresses only for the BSC testnet deployment, and use `STAKING_CONTRACT_VERSION` that matches the deployed contract. This repository is a testnet prototype and is not approved for mainnet or real-fund use.

## Admin user management

After logging in, users can open `/referrals.html` from the account dashboard to see their referral code, shareable link, direct referral count, and referred users' masked email addresses. Referral data requires an authenticated session.

Registration requires a first and last name, a valid TRON USDT TRC-20 address, email, and a password; users must verify their email before signing in. The account dashboard displays the registered TRC-20 address and separate USDT and STAKEAI balances. These are platform-recorded balances, start at zero, and are not read from a blockchain. Older accounts created before address collection show that no TRC-20 address is registered until one is supplied. Users can request internal USDT or STAKEAI balance transfers, and simulated BTC, ETH, or BNB spot-balance transfers, to another active, verified account. USDT recipients are identified by their registered TRC-20 address; token and simulated-asset recipients are identified by their account referral code. BTC, ETH, and BNB transfer requests affect only simulated spot portfolios and never initiate blockchain transactions. Requests appear in the admin panel and do not change balances until approved. Approval debits the sender and credits the recipient in a single database transaction; the sender's balance is checked again at approval time. Funds are not reserved while a request is pending, so a request may remain pending if the sender's balance changes before approval. Rejected requests never change balances.

Users can update their first and last name, change their password, and request an email change from **Profile and security** in the account dashboard. Email changes take effect only after confirmation through the new address; the confirmation link expires after 30 minutes and successful changes revoke all existing sessions. Password changes require the current password, sign out other sessions, and keep the current session active. Users may optionally enable authenticator-app TOTP two-factor authentication; enabling it signs out other sessions. The TOTP secret is encrypted at rest using a key derived from `SESSION_SECRET`; ten single-use recovery codes are shown once, and only their hashes are stored. Enabling or disabling 2FA and changing a password or email requires the current password and, when enabled, a valid TOTP or unused recovery code. Keep `SESSION_SECRET` protected and back it up securely; rotating it invalidates existing sessions and recovery codes and makes stored TOTP secrets unreadable.

Sign in with a verified account whose email is listed in `ADMIN_EMAILS`, then open `/admin.html` (or use the admin link in the account dashboard). For a local, non-production installation with exactly one `ADMIN_EMAILS` address and no account for that address yet, open `/admin-setup.html` from the same computer to create the verified administrator account and choose its password in the browser. This one-time bootstrap is loopback-only, creates a normal password hash, and signs the new account in; it is disabled in production and after the account exists. Do not share passwords in chat. The panel supports pending transfer and task reward approval/rejection, paginated email search, account status, referral information, user names and TRC-20 addresses, and manually editing both balances. Pending request queues refresh automatically every 30 seconds. Balances are stored in exact decimal units (6 places for USDT and 18 for STAKEAI); every actual balance change, including approved transfers and task rewards, is recorded in `balance_audit_log`. Disabling an account immediately revokes its active sessions; administrator accounts cannot be disabled from the panel. Every status change is recorded in `admin_audit_log`. The HTML page itself is public static content, but administrator data and actions are enforced by authenticated, server-side admin APIs.

The testnet staking page connects directly to a user's browser wallet and sends transactions only to the configured BSC testnet contracts. Other account balances and internal transfers remain platform-recorded and are not blockchain balances or transfers. Registration's TRC-20 address remains an administrator reference only; it is not used by staking.

The assistant endpoint is `POST /api/assistants/chat`. It accepts one of the fixed assistant IDs (`code`, `companion`, `strategy`) and up to 10 recent user/assistant messages. Requests are same-origin protected and rate-limited; chat history is held in the browser only. The server sends the prompt to the configured OpenAI-compatible API and never returns or exposes the API key to the browser.

## Market simulator

The home page includes an authenticated paper-trading simulator for BTC, ETH, BNB, and STKAI. It shows public Binance market prices for BTC, ETH, and BNB, and stores each user's separate virtual portfolio, starting with 10,000 virtual USDT. STKAI is shown at a fixed 1 USDT application reference price and can be bought with USDT, BTC, ETH, or BNB; non-USDT quotes are converted using the corresponding live market price. Simulated buys and sells charge a 0.5% commission in the selected quote asset. Commissions settle atomically into a separate, read-only admin pool with an audit history; they are simulated service fees, not blockchain gas. Orders settle atomically against internal admin asset pools and user portfolios, with pool movements recorded in an audit log. The initial virtual treasury inventory is 21,000,000 STKAI and zero USDT, BTC, ETH, and BNB. An admin must seed BTC, ETH, or BNB inventory before users can buy those assets; pools must also hold enough of a quote asset to pay sellers.

The simulator also offers a separate virtual-staking demo for STKAI, USDT, BTC, ETH, and BNB. It uses the displayed 7-day/5%, 30-day/25%, and 180-day/200% examples for every asset. Starting a demo stake locks that asset from the user's virtual portfolio until maturity; claiming returns the principal plus the simulated reward to the same virtual portfolio. These example rates are not guarantees and do not represent a funded or sustainable yield. Virtual stakes never move real tokens or interact with a wallet or blockchain. This demo is separate from the BSC testnet staking flow below, whose on-chain contract accepts STKAI only. All trading/staking balances are part of the app simulation—not blockchain wallets, real reserves, or exchange funds. No real deposit, withdrawal, or blockchain transaction occurs. Market data must be available for simulated trading orders to complete.

## Social task rewards

The task center includes a Telegram group join, an X account follow plus post repost, and a Facebook page follow. Configure `TASK_TELEGRAM_URL`, `TASK_X_PROFILE_URL`, `TASK_X_POST_URL`, and `TASK_FACEBOOK_URL` in `.env` with the official HTTPS destinations; tasks without every required link are unavailable. A signed-in user submits a social username or evidence link for each task. Social actions are not checked automatically: an administrator must review the submission in `/admin.html`. Approving a task credits 10 USDT to the user's internal platform balance, once per task and account, and records the balance change in the audit log. This is an internal balance entry, not an on-chain USDT transfer or guaranteed external payout. Rejected tasks may be resubmitted with updated evidence.

## BSC testnet staking

The package cards submit STAKEAI staking transactions directly from the connected wallet. The testnet-only contracts have three fixed offers: 5% after 7 days, 25% after 30 days, and 200% after 180 days. V1 locks the principal and stores the expected reward; after maturity the user withdraws principal and an administrator sends the reward separately. V2 reserves each reward from a contract-owned reward pool at stake time. At maturity, the user withdraws principal and reward together. A stake is rejected if the unallocated pool cannot cover its full reward. The owner can fund the pool and withdraw only unallocated rewards; rewards reserved for positions cannot be withdrawn. The 200% offer is additional to principal (3x total value).

The site exposes staking only when both `STAKEAI_TOKEN_ADDRESS` and `STAKING_CONTRACT_ADDRESS` are configured. `STAKING_CONTRACT_VERSION` defaults to `1`; set it to `2` when using a newly deployed V2 contract. The browser wallet must be on BSC testnet (chain ID 97). The V2 admin panel lets the contract owner fund or withdraw unallocated rewards directly from a connected wallet. V1 keeps its existing verified manual payout flow. The platform never receives or stores wallet private keys.

For a V2 testnet deployment:

1. Set `DEPLOYER_PRIVATE_KEY` to a dedicated test wallet with testnet BNB for gas. Never use a mainnet key.
2. Run `npm run deploy:bsc-testnet`, then put the printed token address in `STAKEAI_TOKEN_ADDRESS`.
3. Run `npm run deploy:staking-v2:bsc-testnet`, put the printed contract address in `STAKING_CONTRACT_ADDRESS`, and set `STAKING_CONTRACT_VERSION=2`.
4. Restart the server, connect the contract owner's wallet in the admin panel, and fund the reward pool. The owner must approve STAKEAI before funding. Use test wallets only and fund them with test BNB for gas.
5. Add BSC testnet (chain 97) to each wallet and transfer test STAKEAI to users for staking.

V1 and V2 are separate, non-upgradeable contracts, and the app displays one configured staking contract at a time. Positions are not migrated between versions. Before switching to V2, allow existing V1 users to withdraw their principal and receive their manual rewards; otherwise, temporarily restore the V1 address and `STAKING_CONTRACT_VERSION=1` to operate the legacy flow. Switching back to V1 also hides V2 positions until the V2 address/version is restored.

These contracts and rates are a testnet prototype, not audited or approved for mainnet or public financial use. Do not deploy to mainnet or solicit real funds. Production use requires independent contract and application security reviews, legal/compliance review, documented tokenomics and reward funding, monitoring, and a separate mainnet deployment process. The BSC/Bitcoin/Ethereum/TRON payment destinations are configured in `app.js`; update and verify them before deployment. The 1 STAKEAI = 1 USDT statement is a planned target only until reserves, redemption terms, and legal/operational controls actually exist.

## Token development

- `npm test` compiles the contract and runs its tests.
- `npm run compile` compiles without running tests.
- `npm run deploy:bsc-testnet` deploys the token only to BSC testnet.
- `npm run deploy:staking:bsc-testnet` deploys the legacy V1 staking contract.
- `npm run deploy:staking-v2:bsc-testnet` deploys the pre-funded auto-reward V2 staking contract.

The token is named `STAKEAI`, uses the `STKAI` ticker, and mints 21,000,000 tokens once to the deployer with no mint function. The market simulator displays STKAI at a fixed 1 USDT application reference price; this is not an exchange quote, a backed peg, or a redemption guarantee. Deployment scripts refuse any chain other than BSC testnet. Referral rates remain proposals; the fee-recording endpoint is internal and requires a separately configured `INTERNAL_SERVICE_API_KEY`.

ERC-20 token metadata cannot be changed after deployment. Existing token contracts retain their original ticker; using `STKAI` on-chain requires deploying a new token contract and updating `STAKEAI_TOKEN_ADDRESS` and the staking contract configuration to use that deployment.

This is not a production launch checklist. Before handling real users or funds, complete independent smart-contract and application security reviews, legal/compliance review, production secrets and email setup, monitoring, backups, and operational testing. Mainnet deployment is intentionally not enabled by the deployment script.
